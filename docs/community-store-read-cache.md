# Community store read cache

## Scope

The file-backed community store re-read, re-parsed and re-validated the whole
JSON document on every `read()` call. Every public community read request
therefore paid O(whole store) synchronously on the event loop before it could
filter a handful of records.

This change adds a validated snapshot cache to `FileCommunityStore`, keyed by a
file fingerprint. It does not change the document format, the public API, the
routes, the Postgres store, or any response body. Freshness stays a hard
contract: there is no TTL and no stale window. A write through `change()` is
visible to the very next `read()`, and so is an edit made by another process.

## The mechanism

`read()` previously did four things on every call: `existsSync`, `readFileSync`,
`JSON.parse`, then `validate()`. A micro-benchmark separates the cost of each
step on both fixtures, with 300 iterations and no HTTP or load driver:

| component      | 1.01 MB p50 | 4.03 MB p50 |
| -------------- | ----------: | ----------: |
| full `read()`  |    1.908 ms |    8.284 ms |
| `existsSync`   |    0.001 ms |    0.001 ms |
| `readFileSync` |    0.472 ms |    1.916 ms |
| `JSON.parse`   |    1.313 ms |    5.562 ms |

`JSON.parse` is about 67 percent of the cost on the large fixture and about 69
percent on the small one. `existsSync` is negligible. The dominant cost is
therefore parsing, not file I/O.

The cache replaces those four steps with one `statSync` and a fingerprint
comparison. The fingerprint is `dev:ino:size:mtimeMs:ctimeMs`. On a match,
`read()` returns a shallow copy of the frozen snapshot. On a miss it reads,
parses and validates exactly as before, then freezes the result deeply and
stores it.

Three properties follow, and each has a regression test:

- `validate()` still runs on every cache miss and is never skipped. A corrupt or
  hand-edited document throws and is never cached as valid, so reads keep
  failing until the file is repaired.
- The snapshot is deep-frozen. A caller that tries to mutate a nested record
  throws a `TypeError` instead of silently corrupting the shared snapshot for
  every other reader. ES modules are strict mode, so the write cannot fail
  silently.
- `change()` never mutates or reuses the cached snapshot. It invalidates the
  cache first, then reads and parses a fresh document, applies the caller's
  function, and runs the unchanged durable write sequence: temp file, `fsync`,
  rename, directory `fsync`.

A `size` field alone would be insufficient, because a same-length rewrite does
not change it. A test covers exactly that case (`'aaaa'` to `'bbbb'`).

## Before and after

Measured on 2026-11-18 with Node v24.22.2 on the base commit `a0d08a9` and on
this branch. Both fixtures are synthetic community stores generated by the
benchmark harness: 1.01 MB with 2,500 comments, 100 news items and 40 episodes;
4.03 MB with 10,000 comments, 400 news items and 100 episodes.

The load driver is a custom `node:http` open-loop client with a fixed arrival
rate and one monotonic clock for both scheduling and latency, so dispatch delay
is included and there is no coordinated omission. The server process is pinned
to core 0 and the driver to core 1. Each row is the median of 3 repetitions of
10 s measured time after 3 s warmup. Every run had zero errors and zero 429
responses.

Rate was chosen per fixture below the saturation knee. On the 4.03 MB store the
server saturates near 130 req/s, so the large fixture runs at 60 req/s; the
small fixture runs at 150 req/s.

### Why the control matters

`/sitemap.xml` does not read the community store. It stays sub-millisecond at
both fixture sizes, before and after, with CPU near 3 percent. That isolates the
store re-parse as the cause: the HTTP layer, the routes and the response
serialization are not what scaled with the fixture size. Only the endpoints that
re-parsed the store did.

### What remains

`/api/campaigns/:id/comments` is still the slowest endpoint after the change,
and that is expected. Its remaining cost is on the caller side, not in the
store. `listComments` calls `Object.values(state.comments)`, which materializes
every comment before filtering. On the 4.03 MB fixture that is 1.75 ms of the
2.03 ms spent in the whole filter-and-sort step, and it is why comments sits at
3.36 ms while the other endpoints fall to 0.5-0.8 ms. Indexing comments by
campaign would remove it, but that is a separate change to the document shape
and is deliberately out of scope here.

## Reproducing

The harness is not committed, because it is a one-off measurement tool and the
repository keeps no benchmark directory. It consists of five small Node scripts:
a fixture generator, an open-loop driver, a summarizer, a server launcher, and
the micro-benchmark above. The shapes that matter are:

- Fixtures are generated as a valid version-1 document and written with compact
  JSON, so `JSON.parse` cost is not inflated by whitespace.
- The server runs the production build with `NODE_ENV=production` and an
  effectively unlimited read limit, so the read limiter cannot mask latency.
- The driver reports per-path percentiles plus system CPU busy percent from
  `/proc/stat` and server CPU seconds from `/proc/<pid>/stat`.

Treat these numbers as local sandbox measurements on a synthetic fixture. The
4.03 MB fixture is larger than an early-stage deployment, so the figures show
the shape of the cost and its removal. They are not a staging or production
capacity claim.
